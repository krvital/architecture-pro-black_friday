# MP-ADR7 Использование Cassandra для высоконагруженных компонентов интернет-магазина
**Дата:** 15.03.2026

**Автор:** Виталий Кравцов

### Контекст

Во время «чёрной пятницы» система на MongoDB с range-based sharding столкнулась с проблемами масштабирования:

- При добавлении новых шардов происходило полное перераспределение данных.
- Это приводило к росту latency из-за активных миграций чанков.
- Наблюдалась неравномерная нагрузка (hot shards) из-за популярных категорий.

Требования к новой системе:

- Высокая отказоустойчивость (leaderless replication).
- Быстрое горизонтальное масштабирование без полной ребалансировки.
- Равномерное распределение данных.
- Поддержка высокой нагрузки.

Рассматривается использование Cassandra.

### Решение

Принято решение использовать Cassandra как дополнительное хранилище для данных с высокой нагрузкой и допустимой eventual consistency, а не как полную замену MongoDB.

#### Выбор данных для переноса в Cassandra

**Классификация данных**

| Данные/операции | Cassandra | Комментарий                                |
| --------------- | --------- | ------------------------------------------ |
| Каталог товаров | Да        | read-heavy, допустима eventual-consistency |
| Цены товаров    | Да        | допустима eventual-consistency             |
| Остатки товаров | Нет       | требуется атомарность                      |
| Корзины         | Да        | write-heavy                                |
| История заказов | Да        | read-heavy                                 |
| Создание заказа | Нет       | требуется атомарность                      |
| Аналитика       | Да        | допустима eventual-consistency             |

**Данные и соответствующие операции, которые переносим в Cassandra** 

- чтение каталога товаров
- создание и обновление корзины товаров
- чтение истории заказов
- логи и аналитика

**Данные и соответствующие операции, которые оставляем в MongoDB** 

- запись и чтение для остатков товаров
- создание и обновление заказов



#### Концептуальная модель для сущностей в Cassandra

Query-driven design является основным принципом моделирования сущностей в Cassandra и подобных БД. Следовательно, сущности будем проектировать исходя из того, какие сценарии использования требуются для приложения.

**Каталог товаров**

```sql
CREATE TABLE products_by_category (
  category TEXT,
  price_bucket INT,
  product_id UUID,
  name TEXT,
  price DECIMAL,
  PRIMARY KEY ((category, price_bucket), price, product_id)
);
```

Ключи:

- partiition key: `(category, price_bucket)`
  Составной ключ решает проблему hot partition, price_bucket искусственно дробит категорию на несколько партиций и вычисляется на стороне приложения.
- clustering keys: `price`, `product_id` 

**История заказов**

```sql
CREATE TABLE orders_by_user (
  user_id UUID,
  order_date DATE,
  created_at TIMESTAMP,
  order_id UUID,
  status TEXT,
  total_sum DECIMAL,
  PRIMARY KEY ((user_id, order_date), created_at, order_id)
) WITH CLUSTERING ORDER BY (created_at DESC);
```

Ключи:

- partiition key: `(user_id, order_date)`

  Здесь `user_id` нужен для равномерного распределение по нодам, а `order_date` для контроль размера партиции, чтобы история одного пользователя не росла бесконечно на одной ноде.

- clustering keys: `created_at DESC`, `order_id` 

**Корзина**

```sql
CREATE TABLE carts_by_user (
  user_id UUID,
  product_id UUID,
  quantity INT,
  updated_at TIMESTAMP,
  PRIMARY KEY ((user_id, bucket), product_id)
);
```

Ключи

- partition key: `user_id`
  Каждый пользователь пишет и читает только свою партицию. Пользователь A никогда не трогает партицию пользователя B. Это означает, что при 50K RPS нагрузка распределяется по 50K разным партициям одновременно, а не концентрируется в одной.
- clustering keys: `product_id



#### Выбор стратегий обеспечения целостности данных

**Каталог товаров**  (products_by_category)

| Стратегия      | Применять? | Комментарий                                               |
| -------------- | ---------- | --------------------------------------------------------- |
| Hinted Handoff | Нет        | потеря одного обновления не критична (можно перезаписать) |
| Read Repair    | Да         | частые чтения, следовательно данные “самоисправляются”    |
| Anti-Entropy   | Да         | гарантирует, что редкие записи тоже синхронизируются      |

**История заказов** (orders_by_user)

- append-only
- важно не потерять данные
- читается регулярно, но не всегда сразу

| Стратегия      | Применять? | Комментарий                                                  |
| -------------- | ---------- | ------------------------------------------------------------ |
| Hinted Handoff | Да         | нельзя терять заказы                                         |
| Read Repair    | Да/Нет     | заказы читаются не всегда, следовательно не гарантируется repair |
| Anti-Entropy   | Да         | гарантирует eventual consistency                             |

**Корзина** (carts_by_user)

- write-heavy
- частые обновления
- допустима временная неконсистентность

| Стратегия      | Применять? | Комментарий                                                  |
| -------------- | ---------- | ------------------------------------------------------------ |
| Hinted Handoff | Да         | чтобы не терять изменения пользователя                       |
| Read Repair    | Нет        | корзина постоянно перезаписывается                           |
| Anti-Entropy   | Нет        | данные мало живут и eventual consistency достигается обновлениями |
